# mos_itsm_automation_rule_descriptor

Скилл формирует описание работы правила автоматизации МосИТСМ и записывает его в поле
[Описание] карточки этого правила через REST API.

Вход: ссылка на правило автоматизации (или его ID), среда размещения (ПРОД/QA), при
необходимости — токен авторизации. Выход: заполненное поле [Описание] в карточке правила.

## Конфигурация

Все параметры окружения — в `skill_env.json` рядом с этим файлом:
базовые URL API (`MOSITSM_API_URL_PROD`, `MOSITSM_API_URL_QA`), аккаунт (`MOSITSM_ACCOUNT`,
значение `community`), токены (`MOSITSM_PERS_TOKEN_QA`, `MOSITSM_PERS_TOKEN_PROD`).
Среда по умолчанию берётся из `MOSITSM_STAGE` (сейчас QA). TLS корпоративного контура не
проверяется — скрипт работает с непроверенным сертификатом.

## Инструменты

Скрипт `scripts/ar_rule.py` (только стандартная библиотека Python):

```bash
# скачать правило целиком (в JSON, по умолчанию в backups/) — всегда первый шаг
python scripts/ar_rule.py get --rule https://community.itsm-qa.mos.ru/automation_rules/15361146
python scripts/ar_rule.py get --rule 15361146 --env PROD --out rule.json

# записать описание из файла (перед записью сам делает бэкап текущего описания)
python scripts/ar_rule.py set-description --rule 15361146 --file desc.md --dry-run
python scripts/ar_rule.py set-description --rule 15361146 --file desc.md --yes

# проверить, что description на сервере совпадает с файлом, и вёрстку таблиц
python scripts/ar_rule.py check --rule 15361146 --file desc.md
python scripts/ar_rule.py check --rule 15361146   # только вёрстка description_html
```

`--rule` принимает и полный URL, и числовой ID. `--token` переопределяет токен из
`skill_env.json`. Скрипт шлёт только `PATCH {"description": ...}` — другие поля правила
не изменяются никогда.

## Порядок работы

1. **Составить план и согласовать его с пользоваелем** Описать план будущих действий, указать какое правило будет описано, на какой среде, запросить персональный токен, если он не заполнен в `--env QA` и `--env PROD`.
2. **Извлечь ID и среду** из запроса пользователя. Среда: QA → `--env QA`, ПРОД → `--env PROD`.
3. **Скачать правило**: `ar_rule.py get --rule <ID>`. Файл JSON — источник истины: поля
   `name`, `trigger`, `condition`, `expressions`, `actions`, `description` (текущее описание).
4. **Проанализировать** правило: что за объект оно обслуживает (запрос/задача/КЕ — видно из
   `name` и содержимого выражений), на какое событие реагирует (`trigger`), при каком
   условии срабатывает (`condition` — имена расшифровываются через `expressions`), что делает
   (`actions`). Если операторы или функции в выражениях непонятны — прочитать
   `references/operators_extract.txt` (справочник выражений, значений и операторов).
5. **Сгенерировать описание** строго по шаблону из `references/description_template.md`.
   Эталон стиля — `references/reference_description.md` (описание правила 15361146).
   **HTML-таблицы писать только построчно** — каждый тег и текст ячейки на своей строке
   (кроме связки открывающего тега строки и первой ячейки). Таблицы «в одну строку»
   серверный рендерер экранирует, и они превращаются в нечитаемый текст — это реальная
   ошибка, уже приводившая к браку (правило 16292920, 2026-09-21).
   Если у правила уже есть описание с разделом «История изменений» — историю сохранить как есть.
6. **Показать сгенерированное описание пользователю** и записать его только после явного
   согласия (или если пользователь сразу сказал «запиши/обнови»). Запись: сохранить текст в
   `desc_<id>.md`, затем `set-description` (сначала `--dry-run`, потом `--yes`).
7. **Проверить результат**: `ar_rule.py check --rule <ID>` — команда сверяет description с
   файлом (если передан `--file`) и автоматически проверяет вёрстку `description_html`;
   при обнаружении экранированных тегов она падает с ошибкой — в этом случае переписать
   таблицы построчно и записать заново. Затем сообщить пользователю ссылку на карточку:
   `{MOSITSM_BASE_URL_<среда>}/automation_rules/<ID>`.

## Справочные материалы (references/)

- `description_template.md` — шаблон поля [Описание] и правила наполнения.
- `reference_description.md` — эталонный образец (описание правила 15361146).
- `operators_extract.txt` — справочник выражений, значений и операторов языка правил.
- `vendor_api_automation_rules.html` — офлайн-копия документации вендора по Automation Rules API.
- `vendor_rest_api.html`, `vendor_operators.html` — офлайн-копии смежных разделов документации.
- Онлайн-документация: `VENDOR_DOC_URL` из `skill_env.json`.

## Техника безопасности

- Перед любой записью скрипт сохраняет бэкап в `backups/rule_<id>_<дата>.json`; бэкапы не удалять.
- Не отправлять в PATCH ничего, кроме `description`; не трогать `actions`/`condition`/`expressions`.
- Описание больше 64KB API не примет — сокращать текст.
- Для ПРОД-среды токен должен быть явно передан пользователем или лежать в
  `MOSITSM_PERS_TOKEN_PROD`; если его нет — запросить у пользователя, не угадывать.

# Шаблон поля [Описание] правила автоматизации

Формат — Markdown, таблицы записываются как HTML (`<table>...</table>`), потому что редактор
описания в карточке правила рендерит именно HTML-таблицы. Блоки `<c #0f1115>` в первом
абзаце — часть вёрстки эталона, можно опускать.

## КРИТИЧНО: HTML-таблицы только построчно

**HTML-таблицы запрещено писать «в одну строку»** (`<table><tr><td>...</td></tr></table>`
сплошным текстом, включая `</th><th>` и `</td><td>` на одной строке между содержимым).
Серверный рендерер в этом случае экранирует часть тегов (`&lt;/th&gt;&lt;th&gt;...`),
и таблица превращается в нечитаемый текст. Это уже происходило на практике.

**Единственно допустимый формат** — каждый тег и текст ячейки на своей строке:

- `<table><tr><th ...>` — открывающий тег строки и первая ячейка держатся на одной строке
  (как в эталоне), но **текст ячейки всегда с новой строки**, закрывающие `</th>`/`</td>` —
  тоже с новой строки;
- аналогично `</th></tr><tr><td ...>` — одной строкой, дальше текст ячейки с новой строки;
- закрывающий `</table>` — на своей строке.

Пример корректной строки-разделителя: `</th></tr><tr><td style="text-align:left">`.
Пример НЕкорректной ячейки: `<td style="text-align:left">Текст ячейки</td>` (текст и
закрывающий тег на одной строке — так нельзя).

Проверка после записи: `python scripts/ar_rule.py check --rule <ID>` — команда
автоматически проверяет `description_html` и падает, если найдены экранированные теги.

Порядок и заголовки разделов фиксированы. Обновляя существующее описание, раздел
**История изменений** сохраняют как есть (его ведут люди), остальные разделы перегенерируют.

```markdown
## **Описание**

<короткий абзац (3–6 предложений) человеческим языком: на какие записи и события
реагирует правило, при каком условии срабатывает и что делает в итоге — без
перечисления отдельных выражений>

## **История изменений**

<table><tr><th>№</th><th>Дата</th><th>Запрос на изменение</th><th>Автор изменения</th></tr>
<tr><td>1</td><td>ДД.ММ.ГГ</td><td>что изменилось</td><td>автор</td></tr></table>

(для правила без истории — одна строка: дата генерации описания, «Описание сформировано
автоматически», автор — «\-»)

## Настройки правила

<table><tr><td>**Параметр**</td><td>**Значение / Описание**</td></tr>
<tr><td>Триггер</td><td>`{trigger}` — {русское описание триггера}</td></tr>
<tr><td>Условие</td><td>`{condition}` — {расшифровка каждой части условия по имени выражения}</td></tr></table>

## Выражения

<table><tr><th>Имя выражения</th><th>Логика</th></tr>
<tr><td>{name}</td><td>`{выражение как в API}` — {смысл: что проверяет/вычисляет}</td></tr>
...</table>

## Действия

<table><tr><th>Действие</th><th>Описание</th></tr>
<tr><td>{actionN: выражение}</td><td>{что именно произойдёт с записью}</td></tr>
...</table>
```

Правила наполнения:

- Каждому выражению из `expressions` — своя строка в таблице «Выражения», порядок как в API.
  Текст в бэктиках копируется дословно из API (квадратные скобки экранируются `\[`).
- В таблице «Настройки правила» условие расшифровывается через имена выражений: для каждого
  имени из `condition` — краткий человеческий смысл через запятую.
- В таблице «Действия» каждая строка `actionN` из `actions` получает отдельную строку.
- Многострочные тексты (тексты комментариев) в таблице «Выражения» сокращают до первой
  фразы + «...», но обязательно называют назначение текста.
- Русские названия статусов/причин давать по смыслу (например `completed` — «Завершено»,
  `no_reply` — «Нет ответа», `waiting_for_customer` — «Ожидание действий клиента»).
- Не выдумывать то, чего нет в правиле: если назначение выражения неоднозначно, писать
  фактическую формулу и осторожную трактовку.

## Справочник триггеров (trigger из API)

| trigger | Как писать в описании |
|---|---|
| `on created` | при создании записи |
| `on updated` | при любом обновлении записи |
| `on status update` | при изменении статуса записи |
| `after delay` | после задержки по времени (`after_delay`) |
| `on note added` | при добавлении комментария |
| `on internal note added` | при добавлении внутреннего комментария |

Для значений, которых нет в таблице, перевести по смыслу и оставить исходный код API в бэктиках.

## Ограничения API

- Поле `description` — текст до 64KB; `description_html` read-only, генерируется сервером.
- PATCH отправляет только `{"description": "..."}` — остальные поля правила не трогать.
